Alguien tiene que llevar las cuentas

Cuando le pagás a alguien, un banco actualiza su libro contable: resta de tu cuenta y suma en la otra. Funciona, pero ese libro lo tiene una sola entidad:

  • puede congelar, censurar o equivocarse,
  • tiene horarios, fronteras y comisiones,
  • y solo esa entidad ve el libro completo.

Una blockchain es ese mismo libro, pero copiado en miles de computadoras que se ponen de acuerdo sobre qué se anota.

Probá hacer trampa en un libro compartido

Cinco computadoras (nodos) tienen la misma lista de pagos. Probá los botones.

Hash: la huella digital de los datos

Su hash SHA-256 (64 caracteres):

Cambiá una sola letra y mirá qué pasa.

  • Siempre igual: el mismo texto da el mismo hash.
  • Cualquier cambio, por mínimo que sea, da un hash totalmente distinto.
  • No tiene vuelta: del hash no se puede sacar el texto.
  • Bitcoin y Stellar usan SHA-256; Ethereum usa Keccak-256. La idea es la misma.

Un bloque guarda el hash del anterior

Editá el texto del Bloque 2: se rompe ese bloque y todos los que vienen después.

¿Qué es el nonce? Viene de “number used once”: un número que se usa una sola vez. El minero lo va cambiando (0, 1, 2…) hasta que el hash cumpla la dificultad. En Ethereum, “nonce” también es el contador de transacciones de una cuenta; en Stellar ese contador se llama número de secuencia.

¿Cómo se ponen de acuerdo?

Consenso: las reglas para decidir qué bloque es el siguiente, aunque haya nodos caídos o tramposos.

Bitcoin

Prueba de trabajo

Gana quien resuelve primero el acertijo de los ceros (lo que hizo el botón Minar). Hacer trampa cuesta electricidad y máquinas.

Gasta mucha energía. Un bloque cada ~10 min.

Ethereum, Solana

Prueba de participación

Los validadores dejan plata en garantía. Si hacen trampa, la pierden; si cumplen, ganan recompensas.

Mucho menos energía. Ethereum: un bloque cada 12 s.

Stellar

Acuerdo federado (SCP)

Cada validador elige en qué otros confía, y votan en rondas hasta confirmar el mismo bloque. Sin minería y sin premio por validar.

Un ledger cada ~5 s, final al instante.

El ledger: una foto de toda la red cada 5 s

	

		

			
Cada ledger guarda el estado completo: cuentas, saldos, trustlines, ofertas del DEX y datos de contratos. Más el hash del ledger anterior.

			
Para cerrar uno, los validadores corren el Stellar Consensus Protocol:

			
    
				
  • cada validador elige un quórum de nodos en los que confía,
    • 
				
  • se proponen las transacciones candidatas,
    • 
				
  • se vota, se acepta y se confirma.
    • 
			

		

		

			
1

2
Votarsi es coherente con lo que ya votó

			
3
Aceptarcuando su quórum lo apoya

			
4
Confirmares seguro: cierra y es final

Soroban: los contratos de Stellar

	

		
    
			
  • Rust → WebAssembly. Se compila a un archivo Wasm y se despliega con una dirección C….
    • 
			
  • require_auth() exige la firma de una dirección.
    • 
			
  • Almacenamiento con fecha de vencimiento (TTL).
    • 
			
  • Eventos que el frontend puede escuchar.
    • 
			
  • Simulación: antes de enviar, la red te dice el resultado y la comisión.
    • 
		

		
#[contractimpl]
impl Reputation {
    pub fn review(env: Env, reviewer: Address,
                  subject: Address, rating: u32, …)
        -> Result<(), Error> {
        reviewer.require_auth();
        if !(1..=5).contains(&rating) {
            return Err(Error::InvalidRating);
        }
        let storage = env.storage().persistent();
        storage.set(&key, &review);
        storage.extend_ttl(&key, THRESHOLD, EXTEND_TO);
        …
    }
}

Plata con reglas: Trustless Work

	

		

			
Un escrow es un tercero neutral que guarda la plata y la suelta cuando se cumple lo acordado. Acá ese tercero es un contrato: nadie puede salir corriendo con la plata.

			

				
RolQué hace

				
					
Approveraprueba cada hito (el cliente)

					
Service providerentrega y marca hitos como hechos

					
Release signerlibera la plata

					
Dispute resolverdecide si hay desacuerdo

				
			

		

		

			

				
Single-release

				
Un solo pago al final. Compras, depósitos de alquiler.

			

			

				
Multi-release

				
Un pago por hito. Freelance, bounties, grants.

			

			
Trustless Work despliega un contrato (una dirección C…) por trato. Vos no escribís la lógica del escrow.

  • AGENTS.md: las reglas del proyecto, en un archivo que leen todos los agentes.
    • 
				
  • Skills: manuales cortos que el agente abre solo cuando los necesita.
    • 
				
  • npm run check: el agente verifica cada paso (tests, tipos, lint).
    • 
			

		

		
.agents/skills/
  build-dapp/        idea → app, paso a paso
  trustless-work/     escrows (solo si hacen falta)
  cavos/              login con correo
  scaffold-stellar/   contratos ↔ app
  soroban-contracts/  contratos en Rust
  stellar-basics/     conceptos y errores

	






	
Funciona con el agente que ya usás

	

		

			
AgenteCómo encuentra las skills

			
				
Claude CodeCLAUDE.md importa AGENTS.md; skills como /build-dapp

				
CodexAGENTS.md y .agents/skills; $build-dapp

				
Cursor, CopilotAGENTS.md y .agents/skills

				
Gemini, AntigravityAGENTS.md y .agents/skills

				
OpenCode, Pi y otrosAGENTS.md les dice qué archivo abrir

			
		

		

			
Una sola fuente

			
Las skills viven en .agents/skills (estándar abierto). Para las herramientas que buscan en otro lado hay copias sincronizadas, y si un agente no soporta skills, igual las lee porque AGENTS.md le dice dónde están.

		

	






	
Lo probamos con una sola frase

	

		

			
“Quiero una app para vender distintos artículos usando escrows”

			
    
				
  • contrato de publicaciones con 11 tests, en testnet
    • 
				
  • tres páginas: mercado, vender y mis pedidos
    • 
				
  • un escrow por compra, con roles bien puestos
    • 
			

			
Unos 17 minutos, npm run check en verde.

		

		

			
“Quiero hacer una aplicación de votaciones para encuestas”

			
    
				
  • no usó escrows: nadie guarda plata
    • 
				
  • preguntó: ¿voto abierto o secreto?, ¿quién puede votar?, ¿login con correo?
    • 
				
  • contrato con 12 tests y tres páginas en español
    • 
			

			
Unos 17 minutos, npm run check en verde.

Manos a la obra

	

		

			
En GitHub: Use this template para crear tu propio repo, clonalo y corré:

			
npm run setup:tools
npm install
npm run doctor
npm start

			
En app/.env va el App ID de Cavos y, si tu idea usa escrows, la API key de Trustless Work. Los pasos están en el README.

Si algo falla

	

		

			
Ves estoSignifica

			
				
op_no_trustfalta la trustline de USDC

				
underfundedno hay saldo suficiente: Friendbot o swap

				
op_low_reserveno alcanza el saldo mínimo de la cuenta

				
Error(Contract, #3)el contrato rechazó la acción (error número 3)

				
network mismatchtu wallet no está en Testnet

				
Trustless Work 401falta o está mal la API key

			
		

		

			
Primero, esto

			
npm run doctor

			
Revisa herramientas, app/.env, la red y tus claves. Si no, buscá la transacción en stellar.expert o pegale el error a tu agente: tiene un decodificador de errores en las skills.
